# Orchestration troubleshooting

Reference material for plugins/fusion/rules/orchestration.md. This file is not synced to ~/.claude/rules and nothing installs it automatically; it exists for the orchestrator to consult when a delegation is failing, not as an always loaded rule. Codex runtime recovery must also preserve the foreground and durability invariants stated below.

## Escalation ladders

Failure driven implementation escalation among Claude workers runs only from `fusion:trivial-worker` to `fusion:fast-worker`; `fusion:deep-reasoner` is a separate advisory lane. Peer failures are handled by the circuit breaker table below instead.

- Diagnose the brief before the engine: a starved worker looks exactly like a weak one, and most "it just did not do the work" failures are under specified briefs, not capability gaps. Hold the failed brief against the dispatch gate (goal, constraints, relevant paths, done criteria, verification command); if a piece is missing, complete the brief and re-dispatch at the same execution lane. When an exact tiny brief exceeds `fusion:trivial-worker`, move it to `fusion:fast-worker` or an eligible peer implementation lane with the failure attached. `fusion:deep-reasoner` is a read only advisory lane and never receives an implementation brief as an execution retry; ask it to diagnose a hard failure, then let the main session write a new resolved execution brief for the appropriate builder. Do not fix a delegate's botched output in the main loop. The circuit breaker takes precedence: a broken engine is never a rung.
- Quality driven escalation runs alongside the failure ladder: a completed run can still fail review. When the output is correct but below the quality bar, re-dispatch the same brief plus concrete critique to the appropriate stronger execution lane without asking. For Claude implementation, the only tier escalation is from `fusion:trivial-worker` to `fusion:fast-worker`; `fusion:deep-reasoner` may diagnose or critique but never executes the revised implementation brief. Never accept substandard output just because the cheaper lane technically succeeded; judge the output, not the price tag.

## Failure kinds and the circuit breaker

The shared companion failure kinds are quota, auth, missing_cli, rate_limited, timeout, error, permission, cancelled, input, died, and resource. Codex additionally emits protocol when the required JSONL lifecycle is incompatible or malformed, and process for an unexpected process signal. The max turns and session limit entries below are orchestrator observed conditions, not companion failure kinds: max turns arrives as an error result with a max-turns message, and session limit is a Claude-side event. The missing agent type and unavailable line are also observed routing conditions. For engines that do not emit the shared kinds, map an observed failure onto the closest companion failure kind before acting.

| Failure kind or observed condition | Immediate action | Circuit breaker effect |
|---|---|---|
| quota, auth, missing_cli | Stop retrying this engine | Breaks the engine for the rest of the session |
| rate_limited | Retry once on the same peer | Opens only after a second rate limited outcome from that peer inside the configured breaker lookback with no successful peer job between; one isolated rate limit preserves the retry, and a later successful peer job closes the breaker again |
| timeout | For Codex, split or reroute a package that cannot fit the foreground cap; otherwise resume once in the foreground. Never add `--background` unless the incoming user request already contained it. For Grok, resume once when the compatible session is known; a long package may use managed detachment only when its owning Agent collects to terminal, while a manual receipt requires explicit incoming `--background`. Give every manual retry detached by Fusion orchestration one bounded fusion:job-collector attempt before the turn ends, then report an explicit uncollected receipt if its 540000ms window expires | Escalates to a different executor if the retry also times out; does not break the engine |
| died | Cancel the stale job, then one resume of the thread with the failure attached | Escalates to a different executor if the resume also dies; does not break the engine |
| error | One retry with the failure attached | Escalates after the retry; does not break the engine |
| protocol | Run `/codex:setup`, preserve the event diagnostics, and route the package elsewhere until the installed CLI is inside the supported interval and the adapter contract is restored | Breaks Codex until compatibility is verified |
| process | If the signal was not requested, resume once in the foreground with the failure attached; reroute if the second process also terminates unexpectedly | Does not break the engine after one isolated signal; repeated process failures escalate |
| resource | Follow the recorded conflict. For a busy workspace or resumed session lease, collect, cancel, or finish the current owner before reusing it; route independent work through the worktree admission ladder or start a fresh thread instead of resuming concurrently. For an ambiguous legacy id, repeat the lifecycle command with `--cwd`. Reduce or split only when the diagnostic names an output or artifact size limit | Does not break the engine; repeated output overflow should be reported as an adapter compatibility issue |
| permission | Re-dispatch once with `--write` only when repository changes or command execution are acceptable. Otherwise rewrite the Grok consult brief to use file read, list, and search tools only, plus web search and fetch when explicitly enabled. A permission failure on an in-scope read only tool is a hard tool policy regression to report. A repeated /grok:review permission death on the same diff routes to /codex:adversarial-review or fusion:deep-reasoner instead | Does not break the engine; this is a tool policy mismatch, not model misbehavior |
| cancelled | Confirm with the user before treating the work as intentionally dropped | An externally killed job can also report cancelled, so verify before trusting it |
| input | Correct the rejected request before dispatching again | Does not break the engine |
| max turns message on an error result | Hitting max turns on the first attempt marks the package as too big for the lane; split the package or reroute it as a spec grade codex brief; never retry the same brief at the same scope | Does not break the engine |
| Claude-side session limit event | When the harness quota kills a worker and the Agent failure names a reset time, preserve the package brief verbatim in the visible reply so it can be re-dispatched unchanged after the reset; never rewrite it from memory | Does not break the engine |
| missing agent type or a `grok unavailable:` line | Route to the fallback lane | Breaks immediately |

When an engine is broken, use the other peer only where its lane ownership or a protected role fits. Codex failure may send bounded, isolated work to Grok under `burst`; Grok failure sends ordinary implementation back through the Codex admission ladder. Use fusion:fast-worker for Claude-only tools, privacy, or packages outside the remaining peer's safety boundary, and fusion:deep-reasoner for read only adversarial advice.

## Collection repair

A manual receipt returned by a peer Agent to Fusion orchestration is valid but not collected. Dispatch fusion:job-collector with that job's status and blocking result commands before the turn ends. The collector makes one foreground attempt of at most 540000ms. If it times out, the job remains uncollected and the user must receive the job id plus result command. Direct Codex or Grok commands with explicit `--background` return manual receipts whose users inspect progress through status and collect through result; monitors are notification only. Managed Grok detachment never crosses the owning Agent boundary and must finish through its internal result wait chain, whose terminal result records successful companion collection. The monitor suppresses that collected job and emits a delayed fallback after the grace period when a terminal managed job remains uncollected, as a best effort owner loss fallback. A Codex foreground final or managed Grok final containing only a receipt is a contract failure. Do not normalize unauthorized Codex detachment by collecting it; cancel any discovered job, then retry one bounded foreground package or route it elsewhere. When an agent references completed content invisible to the parent, resume that agent once via SendMessage and demand the full deliverable verbatim in its reply, explicitly stating that the parent receives only the final message.

## Died process detection

A running status from an explicitly detached job is a claim, not verified progress. A worker process that dies without recording an outcome (a crash, a reboot, a stream reconnect that never recovers) can leave its job reporting running indefinitely. Before continuing to wait on any detached job whose log has gone quiet, verify liveness rather than trusting status.

The Codex and Grok companions run this check themselves and report such jobs as failure kind died. Codex status, result, and cancel perform the authoritative locked liveness check. Fusion monitor and ordinary stats observation paths never signal a recorded PID or repair a canonical Codex record, and a monitor dead notice remains advisory until status or result confirms it. The explicit stats prune command is cleanup, not liveness repair. A dead process behind a running status is a died outcome, not a slow one: collect or cancel the stale job through the companion, resume the thread once with the failure attached, and if that resume also dies silently, finish the package on a different executor instead of resuming a third time.

## Worker reuse and thread rotation

Worker reuse is scoped and rotated. A follow up instruction may go to the same worker via SendMessage only when it modifies the same files or surface as that worker's previous brief; a new work package, a different surface, or anything that can run in parallel gets a fresh agent instead of queueing behind a warm one.

Reuse is capped: after about three follow up resumes, or when completion notifications show the worker's accumulated usage nearing its context window, rotate to a fresh worker whose brief carries the accumulated decisions and current state rather than assuming the old thread's memory. Truncation resumes complete an existing brief under the same rule but still grow the same context, so they count toward rotation.

The same rotation discipline applies to every warm peer thread, whether kept alive with Grok's `--resume-last` or continued with Codex `--resume` or `--resume-last`. A peer thread whose accumulated context has grown very large is the kind most likely to die mid stream, so rotate it to a fresh thread carrying the accumulated decisions instead of resuming it again.

Warm thread eligibility for `--resume-last`: reuse a warm peer thread only when the new brief continues the same task, files, or subsystem as the prior one, and cannot run in parallel with it. Start a fresh thread for unrelated packages, panels, reviews, and anything dispatched in parallel.
